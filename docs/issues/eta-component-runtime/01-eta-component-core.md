# Eta component runtime core

## Problem Statement

An Eta application that assembles long-lived parts — connection pools, caches,
transports, background workers, plugins — has no runtime that owns their
spatial and temporal composition. Each application rebuilds the same
machinery by hand:

- Dependency wiring is untyped or hand-threaded. A part that needs another
  part receives it through a constructor argument, a global reference, or an
  ad-hoc registry. Nothing checks that a supplied value belongs to the
  contract it claims to satisfy.
- Restart is unsound. When one part must be rebuilt with new configuration,
  the application has no protocol that stops the parts that depend on it
  first, keeps the departing value usable during their asynchronous teardown,
  and prevents a stale in-flight activation from publishing after it lost its
  target.
- Partial failure leaks ownership. A part that fails halfway through
  acquisition leaves earlier acquisitions live, and a cleanup failure is
  logged and forgotten. Nothing quarantines the affected part or marks the
  system degraded.
- Reconfiguration is order-dependent. Applying a new configuration through
  incremental mutation makes the final state depend on the order in which
  changes arrived, so equivalent inputs settle in different states.
- Nothing is observable. The application cannot ask which parts are active,
  which are waiting for an unavailable dependency, which failed, what the
  retained failure was, or whether a requested change has finished.

Eta supplies effects, scopes, supervisors, causes, and observability, but a
scope only owns a lexically bounded resource. It does not own dependency
availability across activations, generation admission, dependent-first
withdrawal, or convergent reconciliation of a declared desired state.

The [Eta component runtime wayfinder](../../wayfinder/eta-component-runtime/map.md)
adapted the Cordis spatiotemporal composability semantics to Eta across 23
resolved decisions, and its
[integrated handoff](../../wayfinder/eta-component-runtime/assets/integrated-handoff.md)
is the approved implementation contract. This spec turns the core of that
contract into requirements.

## Solution

Ship the optional `eta_component` package. It exposes the `Eta_component`
façade: a component runtime whose declarations are statically typed, whose
lifecycle authority is an immutable desired-state tree, and whose observations
are immutable snapshots and settlement reports.

An author declares a **component**: a reusable declaration with a typed
configuration, a typed **requirement** schema, a typed **provision** schema,
an activation-error renderer, and one activation effect. Activation receives
its configuration, its resolved requirement values, and an `Activation.t` that
can own tracked effects whose lifetime extends to activation settlement.

An application builds an immutable **desired-state** tree of groups and
entries, then submits it to a **component context** created by `Context.run`.
The context is the single lifecycle authority. It admits whole snapshots,
rejects duplicate providers and dependency cycles before it mutates anything,
constructs component instances, resolves each activation against one immutable
committed provider view, publishes a complete provision set at one commit
point, and withdraws dependents before their providers.

Every accepted context operation — `reconcile`, `retry`, `replace`,
`shutdown` — returns one settlement fence whose terminal report is immutable
and repeatable. A read-only `Diagnostics.t` supplies atomic snapshots and
coalesced change waits over context lifecycle, progress, integrity, instance
phases, generations, provider episodes, committed views, and opaque failures.

Failure is never silent: an activation failure stays local to one instance and
retains its complete Eta cause, a recovery failure quarantines that instance
and degrades the context, and a runtime invariant violation fails the whole
context with its cause.

## Requirements

In this section, "the system" is the `eta_component` package: the
`Eta_component` façade, its private implementation modules, and the Eta
substrate seams it uses.

### Package and public surface

- The system shall publish the optional `eta_component` package with one public Dune library and one `Eta_component` top-level façade. ^ecpkg-j50r
- The system shall declare `eta` and `eta_observability` as the only Eta package dependencies of `eta_component`. ^ecpkg-xd8q
- The system shall expose the façade submodules `Coeffect`, `Requirement`, `Provision`, `Activation`, `Component`, `Entry_id`, `Desired_state`, `Source_revision`, `Replacement`, `Context`, and `Diagnostics`. ^ecpkg-zndh
- The system shall keep every declaration-storage, admission, provider-graph, coordinator, reconciliation, replacement, diagnostics, and telemetry implementation module private to the package. ^ecpkg-ccgq
- The system shall keep `Eta.Effect.t` at its two existing type parameters and shall add no environment channel, layer, or dynamic provisioning operation to Eta effects. ^ecpkg-42ss
- The system shall install with no Eio, serialization, file-watch, `dynlink`, or test-framework dependency. ^ecpkg-9frs
- The system shall expose no mutable component instance, provider, supervisor, fiber, Eio switch, Eio cancellation value, or Eta runtime token through any public type. ^ecpkg-u9cc
- The system shall keep `Context.t`, `Activation.t`, `Coeffect.t`, `Component.t`, `Diagnostics.t`, and every settlement fence abstract and mode-neutral in the public interface. ^ecpkg-vpiu

### Coeffect contracts

- The system shall provide `Coeffect.create`, which allocates one fresh generative key identity, retains one diagnostic name, and retains one value-equivalence function. ^eccoe-qhal
- The system shall exclude the diagnostic coeffect name from coeffect key identity. ^eccoe-4xfi
- The system shall treat two coeffects that share a value type and have different identities as different keys. ^eccoe-3n2x
- The system shall provide `Coeffect.Interception.create`, which defines one typed metadata type, one empty metadata value, one associative merge operation with that empty value as its identity, and one value wrapper that receives an operation-entry metadata sample. ^eccoe-4nz1
- The system shall derive exactly one coeffect contract from each interception descriptor. ^eccoe-vk9s
- The system shall reject at compile time interception metadata declared for a coeffect that has no interception descriptor. ^eccoe-id9f
- The system shall recover the value type of a stored provision through its key equality witness and shall use no `Obj` operation in the public interface. ^eccoe-rwvx
- The system shall select a provider and preserve an activation generation by provider-episode identity, not by coeffect value equivalence. ^eccoe-r20a
- Where a coeffect declares value equivalence, the system shall use that equivalence only in executable recovery-contract verification. ^eccoe-1zu1
- The system shall provide executable identity and associativity contracts for each interception merge operation. ^eccoe-0vvd

### Component declarations

- The system shall provide `Component.Family.create`, which allocates one stable component family with a diagnostic name and one stable module locator. ^ecdec-hdka
- The system shall provide `Component.make`, which binds one family, one configuration-equivalence function, one requirement schema, one provision schema, one activation-error renderer, and one activation function into a declaration whose only remaining type parameter is its configuration type. ^ecdec-fra1
- The system shall make requirement, provision, and activation-error types existential after `Component.make`. ^ecdec-znn0
- The system shall check `Component.make` schema keys without running any caller callback. ^ecdec-vnmw
- If one schema declares the same coeffect key twice, then the system shall return `Duplicate_requirement` or `Duplicate_provision` with that coeffect name. ^ecdec-oqp1
- If one declaration requires and provides the same coeffect key, then the system shall return `Self_dependency` with that coeffect name. ^ecdec-um4h
- When several declaration errors exist, the system shall return the first error in declaration order. ^ecdec-bjm4
- The system shall provide `Requirement.none`, `Requirement.one`, `Requirement.intercepted`, `Requirement.both`, and `Requirement.map` as the only requirement constructors. ^ecdec-7b2m
- The system shall provide `Provision.none`, `Provision.one`, `Provision.both`, and `Provision.contramap` as the only provision constructors. ^ecdec-8e8x
- The system shall reject at compile time a requirement or provision value whose OCaml type does not match its coeffect value type. ^ecdec-b1z0
- The system shall reject at compile time an entry whose configuration type does not match its component configuration type. ^ecdec-ogw5
- The system shall provide `Component.pack`, which hides the configuration type for heterogeneous loading. ^ecdec-ux8r
- The system shall expose no public `start`, `stop`, or recovery operation on a component declaration. ^ecdec-hvlm

### Desired-state construction

- The system shall provide pure desired-state construction that performs no loading, admission, effect execution, or reconciliation. ^ecdes-m68e
- The system shall require one application-owned stable `Entry_id.t` for every group and component entry. ^ecdes-a1so
- The system shall provide `Entry_id.of_string`, which returns `` `Invalid_entry_id `` for an entry identifier that fails validation. ^ecdes-jd9o
- The system shall treat child position as structural data and not as identity. ^ecdes-leke
- The system shall build a group node that carries enablement and one context specification and creates no component instance. ^ecdes-5gs3
- The system shall provide `Desired_state.Context_spec.isolate`, which binds one coeffect key to one realm for a node and its descendants. ^ecdes-26c5
- The system shall provide `Desired_state.Context_spec.intercept`, which adds typed metadata for one interceptable coeffect for a node and its descendants. ^ecdes-y79w
- The system shall provide `Desired_state.Realm.create`, which allocates one opaque generative realm identity. ^ecdes-y7u8
- The system shall pair one component declaration with one matching configuration in `Desired_state.Entry.make` and shall hide that configuration type in the resulting node. ^ecdes-asei
- The system shall make every constructed desired-state value immutable through its public interface. ^ecdes-otma

### Component-context lifetime

- The system shall create one component context inside one lexical `Context.run` effect and shall supply that context authority and one read-only `Diagnostics.t` to the body. ^ecctx-ok4h
- The system shall allocate one fresh context identity for each `Context.run` lifetime. ^ecctx-895x
- When the `Context.run` body returns, the system shall start shutdown and shall wait for every owned scope to settle before the effect completes. ^ecctx-uvft
- When the `Context.run` body fails, the system shall start shutdown, wait for owned settlement, and preserve the body cause under Eta finalizer and suppression rules. ^ecctx-xv9c
- When the `Context.run` body is interrupted, the system shall start shutdown, wait for owned settlement, and preserve the interruption cause. ^ecctx-dw73
- The system shall grant no reconcile, retry, replace, or shutdown authority through `Diagnostics.t`. ^ecctx-ool6
- The system shall accept `Context.reconcile`, `Context.retry`, `Context.replace`, and `Context.shutdown` as the only context operations. ^ecctx-9p5m
- When the system accepts a context operation, it shall return one settlement fence for that operation. ^ecctx-nmk5
- If a context operation fails admission, then the system shall return one typed `admission_error` and shall create no settlement fence. ^ecctx-3fj2
- If a context operation fails admission, then the system shall change no accepted desired state, component instance, provider binding, or observation revision. ^ecctx-5535
- When the first shutdown request arrives, the system shall create one shutdown fence and shall close admission for every other context operation. ^ecctx-3njw
- When a repeated shutdown request arrives, the system shall return the existing shutdown fence and shall start no additional cleanup pass. ^ecctx-rww9
- If a non-shutdown context operation arrives after shutdown started, then the system shall return `Context_not_running`. ^ecctx-jl3r
- When shutdown is admitted, the system shall supersede every unfinished target and shall wait for every owned scope. ^ecctx-pi1o
- The system shall serialize the admission of every context operation and every atomic state mutation through one context coordinator. ^ecctx-s5x8
- If a component-runtime invariant violation occurs, then the system shall stop the complete component context, retain its cause, and report integrity `Failed`. ^ecctx-oxf3
- The system shall provide `Context.retry` as a context-level request that selects a fresh retry generation for one entry and exposes no component-instance handle. ^ecctx-oyty
- If `Context.retry` names an entry that has no retryable failed instance, then the system shall return `Retry_not_available` with that entry identifier. ^ecctx-tuyy
- If `Context.retry` names a quarantined instance, then the system shall return `Quarantined_instance` with that entry identifier. ^ecctx-mm96
- The system shall keep the complete component context inside one `Context.run` lifetime and shall let no context survive across separate `Runtime.run` calls. ^ecctx-c8dc

### Tracked activation ownership

- The system shall provide `Activation.own`, which admits one tracked effect for the current activation generation and requires an acquire effect, a release function, and a release-error renderer. ^ecact-dcjo
- If `Activation.own` runs for a stale generation or after generation admission closed, then the system shall report requested lifecycle interruption without widening the acquisition error type. ^ecact-8blc
- When an `Activation.own` acquisition succeeds, the system shall register its release with the current Eta activation scope before the operation returns. ^ecact-wr53
- When an `Activation.own` acquisition succeeds after cancellation was requested, the system shall still register its release. ^ecact-jkop
- If an `Activation.own` acquisition fails, then the system shall register no release for that acquisition and shall run every release from an earlier successful acquisition. ^ecact-ld3h
- The system shall run each registered release at most once, including when that release fails. ^ecact-791z
- The system shall run the releases of one activation serially in reverse registration order. ^ecact-gj54
- When one release fails, the system shall run every remaining release and shall retain the failure in the Eta finalizer cause. ^ecact-b5yx
- When repeated disposal requests arrive for one activation, the system shall join one settlement fence, return the same terminal outcome, and run no release again. ^ecact-c6i9
- The system shall invoke `pp_release_error` at most once for one settled failure leaf. ^ecact-cnb5
- If `pp_release_error` raises, then the system shall produce a `Renderer_failed` diagnostic and shall leave the authoritative finalizer cause unchanged. ^ecact-7kqg
- The system shall expose no registry, dynamic lookup, publication operation, child-installation operation, context authority, runtime token, or lifecycle handle through `Activation.t`. ^ecact-xno3
- The system shall attribute every tracked acquisition and release to one component instance and one activation generation in lifecycle diagnostics. ^ecact-eod6
- The system shall let no work from a stale generation publish a provision or admit another tracked effect. ^ecact-ook8
- The system shall implement every specialized component ownership operation through `Activation.own`. ^ecact-31mv
- The system shall add no default cleanup timeout to a release operation. ^ecact-xjvn

### Instance lifecycle, generations, and causes

- The system shall give each component instance one serialized inertial coordinator that keeps the latest desired target separate from the current lifecycle phase. ^eclif-6x6m
- The system shall represent an instance phase as `Inactive`, `Waiting`, `Activating`, `Active`, `Settling`, `Activation_failed`, or `Recovery_failed`. ^eclif-wve2
- The system shall allocate one fresh generation identity for every activation attempt and shall never reuse a generation identity within one component instance. ^eclif-yorn
- The system shall run each activation generation as one private supervisor child with one fresh `Effect.with_scope` lifetime. ^eclif-vqz8
- When a target change arrives, the system shall close generation admission before it requests cancellation. ^eclif-u1cp
- While a generation is stale, the system shall prevent it from committing its staged provisions. ^eclif-ngeo
- When a target changes during `Activating`, the system shall settle that generation's activation result and Eta scope before the next generation starts. ^eclif-aouk
- When a target arrives during `Settling`, the system shall replace the pending target, reverse no settlement, and start no overlapping work. ^eclif-yd28
- When settlement completes cleanly, the system shall start only the latest pending target. ^eclif-zp54
- The system shall commit an activation result only when its generation still matches the current target. ^eclif-ft8e
- When an activation commits, the system shall publish its complete declared provision set at that commit point. ^eclif-da3j
- If a staged provision set is incomplete or stale, then the system shall publish no provision from it. ^eclif-n3ph
- When an activation fails, the system shall close admission and settle every tracked effect before it exposes a terminal failure. ^eclif-htwj
- When activation cleanup succeeds after an activation failure, the system shall enter `Activation_failed`, retain the original cause, and publish no staged provision. ^eclif-nzcr
- When cleanup fails after an activation failure, the system shall retain a `Cause.Suppressed` result that contains both causes. ^eclif-fxvk
- When cleanup fails after a successful primary result, the system shall retain a `Cause.Finalizer` result. ^eclif-0ncu
- The system shall treat requested interruption without another failure as lifecycle control and shall create no activation failure from it. ^eclif-6fwk
- When an unexpected interruption occurs, the system shall retain it as part of the activation cause. ^eclif-zna4
- The system shall retain each generation outcome as an existential same-domain `Eta.Cause` value and shall convert no authoritative failure to a `result`, a string, or a log-only event. ^eclif-gp51
- The system shall keep an activation failure local to one component instance and shall continue lifecycle coordination for unrelated instances. ^eclif-qhoe
- When cleanup fails, the system shall enter `Recovery_failed`, quarantine that instance, and reject every later generation for it in the same context. ^eclif-atqs
- While one instance is quarantined, the system shall report context integrity `Degraded` with every quarantined instance identity. ^eclif-a104
- The system shall keep an activation failure out of context integrity. ^eclif-0qsr
- If a release operation does not terminate, then the system shall keep that instance in `Settling` and shall keep its settlement fence pending. ^eclif-5rgo

### Provider resolution, episodes, and withdrawal

- The system shall index every discoverable provider by one isolation realm and one typed coeffect key. ^ecprv-lx31
- The system shall resolve all declared requirements of one activation as one operation. ^ecprv-lc2c
- While one declared requirement has no discoverable provider episode, the system shall keep that consumer in `Waiting` and shall start no activation for it. ^ecprv-spz5
- When every declared requirement resolves, the system shall form one complete committed provider view that maps each requirement to one provider episode. ^ecprv-sidr
- The system shall keep one consumer's committed provider view unchanged for its complete activation generation, including during its teardown. ^ecprv-98vg
- The system shall supply resolved requirement values to activation code and shall supply no registry, provider callback, or key lookup. ^ecprv-ygrl
- When one generation stages its complete provision set, the system shall allocate one fresh opaque provider-episode identity for it. ^ecprv-1ymi
- The system shall associate each provider-episode identity with exactly one component instance and one activation generation. ^ecprv-zol5
- The system shall allocate a new provider episode for every reactivation and shall preserve no episode identity across generations. ^ecprv-cps5
- When a provider visibility change occurs, the system shall queue only consumers that declare an affected coeffect key in the affected realm. ^ecprv-vlj0
- The system shall treat a topology revision as a notification token that by itself starts no reactivation. ^ecprv-rzy6
- When a queued consumer runs, the system shall recompute its complete target provider view. ^ecprv-nxrp
- When a consumer's committed provider view loses an episode or observes a changed episode identity, the system shall start settlement for that consumer. ^ecprv-4kkg
- The system shall give each consumer episode one lease for each distinct provider episode in its committed view. ^ecprv-3qlf
- Where several required keys resolve to one provider episode, the system shall retain one dependency edge and one lease for that episode. ^ecprv-mp4p
- When a provider episode withdraws, the system shall close its admission, remove it from new resolution, and then close admission for every consumer whose committed view retains it. ^ecprv-o977
- While one direct lease on a provider episode remains, the system shall run no recovery for that provider episode. ^ecprv-3uzf
- When a consumer settles cleanly, the system shall release its direct provider leases. ^ecprv-9cuk
- If a consumer cleanup fails or does not terminate, then the system shall retain its provider leases and shall keep the provider guarded. ^ecprv-sbd7
- The system shall deactivate an active generation through a private normal-stop signal sent after its direct lease count reaches zero, and shall use cancellation only for invalidated activation and forced shutdown. ^ecprv-2s79
- The system shall keep a retiring provider episode undiscoverable while its committed consumer views retain it. ^ecprv-jn7v
- When a distinct successor instance commits a provider episode for a slot the retiring episode left, the system shall make the successor discoverable without waiting for the retiring episode's lease count. ^ecprv-yw14
- The system shall serialize generations within one component instance and shall start no new generation for an instance before its previous generation settles. ^ecprv-t6ni

### Isolation and interception

- The system shall resolve an unisolated coeffect key in the root realm for that key. ^eciso-ibdz
- The system shall let two coeffect keys that use one realm name resolve independently. ^eciso-6n6i
- The system shall inherit realm and interception mappings from one parent context slot and shall let a local mapping shadow its inherited mapping for one coeffect key. ^eciso-fnnl
- The system shall leave a parent context slot unchanged when it derives a child context slot. ^eciso-gugz
- The system shall let no application or activation code mutate a context slot. ^eciso-22fh
- When the system resolves an interceptable requirement, it shall fold component-declared metadata, then outer-context metadata, then inner-context metadata, in that order. ^eciso-t249
- Where a requirement declares no metadata for an interceptable coeffect, the system shall use the empty metadata value and shall still apply context interception. ^eciso-aqjl
- When a coeffect operation starts, the system shall sample one immutable merged metadata snapshot for that operation. ^eciso-1ql3
- While one coeffect operation is in progress, the system shall keep its entry metadata snapshot unchanged. ^eciso-bw67
- When interception metadata changes, the system shall apply the new snapshot to later coeffect operations only, and shall start no reactivation. ^eciso-gulu
- The system shall leave provider availability, provider-episode identity, and each committed provider view unchanged when interception changes. ^eciso-2rw0
- When a realm reassignment is admitted, the system shall commit realm mappings and owned provider-binding transfers together in one coordinator transaction. ^eciso-ctam
- The system shall select provider bindings for transfer by the exact changed effective realm slot and shall leave a nearer realm override independent of an enclosing realm change. ^eciso-zmd9
- When a provider and its consumer move to one realm together, the system shall preserve the provider episode and shall preserve the active consumer generation. ^eciso-jmjf
- If a realm-reassignment destination conflicts, then the system shall reject the transaction before commit and shall leave realm mappings, provider bindings, committed views, and lifecycle state unchanged. ^eciso-o7uw
- When only a consumer moves into an occupied realm, the system shall make the existing provider of that realm its target. ^eciso-cp12

### Admission and reconciliation

- The system shall accept one complete desired-state snapshot as the only component-instance creation authority. ^ecrec-w7fh
- When the system admits a desired-state snapshot, it shall validate that every node identifier is unique before any lifecycle mutation. ^ecrec-pa9m
- If an admitted snapshot repeats a node identifier, then the system shall return `Duplicate_entry_id` with that identifier. ^ecrec-sxm5
- If an admitted snapshot changes the node kind of an identifier whose runtime authority still exists, then the system shall return `Entry_kind_changed` with that identifier. ^ecrec-a1b8
- If two effectively enabled provision declarations select one coeffect-key and realm slot, then the system shall return `Duplicate_provider` with that coeffect name, realm name, and both entry identifiers. ^ecrec-vaf6
- If the prospective provider graph of an admitted snapshot contains a cycle, then the system shall return `Dependency_cycle` with the cycle entry identifiers. ^ecrec-zrsx
- The system shall compute the prospective provider graph from every selected slot and shall reject every cycle before lifecycle mutation. ^ecrec-nfsk
- The system shall treat a missing provider as valid admission and shall leave its consumer waiting. ^ecrec-tmtg
- The system shall check every effectively enabled provision declaration at admission and shall not wait for provider activation. ^ecrec-ubxc
- When the system accepts a validated snapshot, it shall record one desired revision. ^ecrec-z5ss
- The system shall derive every effective group and entry value from the final accepted tree before it starts per-entry lifecycle work. ^ecrec-483i
- The system shall preserve group context slots and component instances by stable identifier across reordering and movement. ^ecrec-aake
- When an entry moves, the system shall update structural parentage and shall preserve component-instance identity. ^ecrec-dad9
- When an entry becomes disabled, the system shall settle its active generation and shall retain an inactive component instance. ^ecrec-h1ni
- When a disabled entry becomes enabled, the system shall start a fresh generation on its retained component instance. ^ecrec-clbi
- When an entry leaves desired state, the system shall settle its instance and then remove that instance identity. ^ecrec-7j8p
- When a removed entry identifier returns to desired state, the system shall allocate a new component instance for it. ^ecrec-ehxa
- When an entry configuration is not equivalent to its committed configuration, the system shall settle the active generation before it starts a fresh generation. ^ecrec-ewm8
- Where an entry configuration is equivalent to its committed configuration, the system shall preserve the current activation target. ^ecrec-vqol
- When a group leaves desired state while a descendant settles, the system shall retain its context slot until the last descendant leaves. ^ecrec-r5u8
- The system shall fence every active or activating provider whose final target must retire, and shall compute that fence to a fixed point before ordinary consumer reconciliation starts. ^ecrec-n1kd
- The system shall let no new resolution observe a fenced provider episode. ^ecrec-hc4z
- After admission, the system shall let each component-instance coordinator read only the latest accepted snapshot and shall apply no incremental tree patch. ^ecrec-6lz2
- Where one initial committed state, one final accepted snapshot, terminating activation, and successful cleanup hold, the system shall reach a quiescent projection that is independent of reconciliation order. ^ecrec-fgwo

### Replacement, rollback, and restoration

- The system shall construct a replacement target from one desired-state entry, one expected instance identity, and one expected target revision. ^ecrep-05te
- The system shall qualify every target revision by its context and shall cover the instance incarnation, enablement, declaration and family identity, stable family module locator, configuration equivalence class, and complete effective isolation and interception context. ^ecrep-8s64
- The system shall leave a target revision unchanged when only child order changes. ^ecrep-547d
- The system shall change a target revision on a move only when its effective target facts change. ^ecrep-lel5
- If a replacement candidate names a component whose family or configuration identity differs from its target, then the system shall return `Component_identity_mismatch` with that entry identifier. ^ecrep-d7s0
- If a replacement batch is empty or repeats an entry identifier, then the system shall return `Empty_batch` or `Duplicate_entry`. ^ecrep-0al3
- The system shall stamp every replacement batch with one source revision. ^ecrep-tgvg
- The system shall reject a submitted source revision that is not greater than the latest accepted source revision of that context, before lifecycle mutation. ^ecrep-vd9u
- If any replacement target carries a stale instance incarnation, a stale target revision, or another context, then the system shall reject the complete batch with the matching typed admission error. ^ecrep-y1vs
- When the system admits a replacement batch, it shall recompute the current participant closure and provider graph under the serialized coordinator. ^ecrep-0cr9
- If a replacement batch names a quarantined instance in its participant closure, then the system shall reject the batch with `Quarantined_instance`. ^ecrep-4wk4
- When lifecycle mutation starts, the system shall retain the current declarations and committed configuration snapshots of the participant closure. ^ecrep-rpcr
- When a replacement transaction starts, the system shall fence every provider in the affected runtime closure and shall settle old generations in consumer-first order. ^ecrep-v5dw
- The system shall start candidate activations in provider-first order and shall treat start and completion as separate lifecycle steps. ^ecrep-9t9c
- The system shall let a staged consumer resolve a staged provider from the same replacement transaction. ^ecrep-7puo
- The system shall keep a staged provider episode undiscoverable to other component instances until the batch commit. ^ecrep-jxiw
- When every candidate completes, the system shall publish all staged provider episodes in one commit. ^ecrep-qb8s
- Where a required provider is unavailable, the system shall commit the new declaration without an activation and shall leave the consumer waiting. ^ecrep-z6ki
- If a candidate installation or candidate activation fails, then the system shall close every candidate attempt and shall restore the declarations and configurations captured immediately before lifecycle mutation. ^ecrep-wv4g
- The system shall stage every successful restoration generation before one coordinator commit and shall use fresh generations and fresh provider episodes for restoration. ^ecrep-qvht
- If a restoration activation fails, then the system shall close every staged restoration attempt, publish no restored provision set, and complete the fence as `Restoration_failed`. ^ecrep-juk6
- If candidate or restoration cleanup fails, then the system shall quarantine that instance, degrade the context, and prevent restoration for that instance. ^ecrep-sfq0
- When rollback publishes the pre-mutation target, the system shall publish it at one linearization point and shall complete that replacement fence as `Rolled_back`. ^ecrep-amml
- If a replacement becomes superseded before publication, then the system shall close every candidate and restoration attempt, restore no obsolete pre-mutation target, and start the latest accepted target after settlement. ^ecrep-ovpf

### Operations, supersession, and settlement outcomes

- The system shall let reconciliation, retry, and replacement overlap in time while it serializes their admission and every atomic mutation. ^ecdia-i0jo
- When a later accepted operation selects a conflicting target, the system shall supersede the earlier operation only for the component instances with that conflicting target. ^ecdia-4b3f
- When two accepted operations select disjoint targets, the system shall let both finish normally. ^ecdia-jx0h
- When one operation is superseded, the system shall wait until all work it started settles before it completes that fence. ^ecdia-fhj1
- The system shall record the fence that started each generation and shall retain that generation in every report that started, retired, or waited for it, with its participant role. ^ecdia-yaeg
- The system shall complete an operation fence with the first applicable outcome in the order `Context_failed`, `Degraded`, `Restoration_failed`, `Rolled_back`, `Superseded`, `Quiescent`. ^ecdia-cj17
- When an activation fails cleanly and settles, the system shall complete its operation fence as `Quiescent` and shall retain its participant and failure in the report and final snapshot. ^ecdia-abcc
- When a cleanup failure completes, the system shall complete its reconciliation, retry, or replacement fence as `Degraded`. ^ecdia-jy1o
- While a retained lease prevents provider settlement, the system shall keep the shutdown fence pending. ^ecdia-xtmt
- If a cleanup operation does not terminate, then the system shall report progress `Reconciling` and shall produce no terminal report for its fence. ^ecdia-2cm7
- When repeated waits arrive for one settled fence, the system shall return the same terminal report. ^ecdia-z7az
- The system shall retain every operation participant in its terminal report after that participant leaves current state. ^ecdia-jt6f
- The system shall include fence identity, operation kind, admission revision, terminal revision, final snapshot, terminal outcome, every participant, and every operation-local retained failure in one terminal report. ^ecdia-6nuk
- The system shall include entry identity, instance identity, participating generations, participating provider episodes, terminal phase or removal, and any failure in each participant record. ^ecdia-ar59

### Diagnostics observation

- The system shall return one atomic projection of the serialized coordinator state from `Diagnostics.snapshot`. ^ecdia-xzif

- The system shall expose no aggregate availability value. ^ecdia-aacx
- The system shall advance the observation revision for every mutation of a snapshot-visible fact and shall use distinct revisions for activation start, activation completion, settlement start, and settlement completion. ^ecdia-tzne

- When `await_change` receives a stale same-context revision for a live context, the system shall return the latest snapshot immediately. ^ecdia-r4sm
- When `await_change` receives the current revision of a live context, the system shall wait for a later snapshot and shall return the latest snapshot when it exists. ^ecdia-2gqs
- When `await_change` receives any valid same-context revision for a closed context, the system shall return `Closed` with the final snapshot immediately. ^ecdia-sh2b

- If `await_change` receives a future same-context revision, then the system shall return `Invalid_revision`. ^ecdia-mx7h

- When several waiters wait on one revision, the system shall deliver the same later snapshot to each of them. ^ecdia-n6an
- When a waiting effect is cancelled, the system shall stop only that waiting effect and shall change no component lifecycle state. ^ecdia-c36z
- The system shall expose no public lifecycle event history or journal. ^ecdia-mbqz
- The system shall let `await_change` coalesce intermediate revisions. ^ecdia-pf45

## Implementation Decisions

The complete design signatures, the callback-boundary table, the provider and
admission rules, the operation and settlement rules, and the implementation
sequence live in the approved
[integrated handoff](../../wayfinder/eta-component-runtime/assets/integrated-handoff.md).
That document is normative for this spec. This section records the decisions
that shape the implementation and must not drift.

**Package.** One optional package `eta_component`, one public library, one
`Eta_component` façade, dependencies `eta` and `eta_observability`. The
private module clusters are declaration storage and interception, admission
and provider graph, context and instance coordinators and generations,
reconciliation, replacement, and diagnostics and telemetry, as fixed in
[Package and module ownership](../../wayfinder/eta-component-runtime/issues/19-package-and-module-ownership.md).
No `eta_component_eio` package: `eta_eio` remains the only Eio adapter and
neither package depends on the other.

**Declaration shape.** Typed requirement and provision schemas without public
declaration rows or context phantoms, per
[Public interface alternatives](../../wayfinder/eta-component-runtime/issues/18-public-interface-alternatives.md).
`'config Component.t` retains only its configuration type; requirement,
provision, and activation-error types become existential at `Component.make`.
Keys are generative `Type.Id` identities and the registry stores existential
bindings:

```ocaml
type binding = Binding : 'a Coeffect.t * 'a -> binding
```

**Tracked ownership.** One public operation, from
[Temporal ownership and recovery](../../wayfinder/eta-component-runtime/issues/11-temporal-ownership-and-recovery.md):

```ocaml
val own :
  Activation.t ->
  acquire:('resource, 'acquire_error) Eta.Effect.t ->
  release:('resource -> (unit, 'release_error) Eta.Effect.t) ->
  pp_release_error:(Format.formatter -> 'release_error -> unit) ->
  ('resource, 'acquire_error) Eta.Effect.t
```

The Eta activation scope is the single recovery authority. The runtime keeps no
second inverse stack and creates no derived context per tracked effect.
`Effect.with_resource` remains the operation for a body-bounded resource.

**Runtime seam.** No component-specific backend contract. One lexical
`Context.run` effect owns one `Supervisor.scoped` nursery; each generation is a
private supervisor child with a fresh `Effect.with_scope` lifetime, started
with `Supervisor.Scope.start`, interrupted with
`Supervisor.Scope.request_cancel`, fenced with `Supervisor.Scope.await`, and
materialized with `Effect.to_exit`. `Eta_eio` interprets the effect in
production and `Eta_test.Run` interprets the same effect deterministically.

**Generation protocol.** Resolve one complete view, allocate a fresh
generation, start the private child, run activation in a fresh scope, admit
tracked work only while the admission fence is open, stage the complete
provision set, commit only against the current target, hold the child on a
private normal-stop signal, and on withdrawal close admission, remove the
episode from resolution, settle lease-holding consumers, send normal stop when
the direct lease count reaches zero, await settlement, and only then start a
later generation.

**Withdrawal guard.** Direct provider-episode leases per consumer episode, one
lease per distinct episode, released on clean consumer settlement. Dependent-
first settlement follows from the direct counts; there is no transitive
counter. Normal deactivation is a normal stop, not a cancellation.

**Desired state.** One immutable typed tree with application-owned stable IDs,
whole-snapshot admission, a global provider-retirement fence computed to a
fixed point, and per-entry coordinators that read only the latest accepted
snapshot. The entry pairs a component with its configuration before hiding the
type:

```ocaml
type node =
  | Entry : {
      id : Entry_id.t;
      component : 'config Component.t;
      config : 'config;
      enabled : bool;
      context : Context_spec.t;
    } -> node
```

**Interception algebra.** Metadata forms a monoid; the fold order is
component, then outer context, then inner context. The wrapper samples one
immutable merged snapshot at each coeffect operation entry.

**Replacement.** A retained entry keeps one component instance; a candidate is
a fresh generation, not a fresh instance. The transaction fences the affected
closure, drains consumer-first, activates candidates provider-first into a
transaction-local staged view, and publishes one batch atomically. Rollback
restores the declarations captured immediately before lifecycle mutation, not a
preparation-time target. Component-local state does not migrate.

**Diagnostics.** Immutable snapshots plus coalesced change waits plus
context-owned settlement fences. No public journal. The authoritative failure
stays an existential same-domain `'error Cause.t`; the public surface is an
opaque `Failure.t` with pre-rendered pretty, compact, and portable
projections.

**Terminal outcome precedence.** `Context_failed`, `Degraded`,
`Restoration_failed`, `Rolled_back`, `Superseded`, `Quiescent`.

**Contract precedence.** The refinements listed under "Contract precedence" in
the integrated handoff are final and override any earlier prototype wording:
two `Effect.t` parameters, reconciliation as the only instance-creation
authority, one opaque episode identity per instance and generation, the
metadata fold order, closed admission reported as requested lifecycle
interruption, a mandatory release-error renderer, schema-key rejection in
`Component.make`, accepted target revisions on replacement candidates, later
accepted targets superseding earlier conflicting ones, and repeated shutdown
returning the first fence.

**Implementation sequence.** Steps 1 to 6 and steps 9 to 10 of the integrated
handoff sequence belong to this spec: declaration foundation, pure semantic
oracle, generation ownership, provider coordination, context control and
reconciliation, replacement, then telemetry and cost gates, then the release
gates. Each step lands its public law prose, its named executable properties,
and its registry rows in the same change.

## Testing Decisions

A good test observes external behavior at a public seam — admission results,
settlement fences and reports, diagnostics snapshots and change waits, opaque
failures, and controlled witnesses — and asserts no private data structure.
Every law-bearing claim added to `eta_component.mli` needs its named
executable gate and its registry row in the same change, per the repository
executable-law policy.

**Seams** (these need user confirmation before implementation starts):

1. The public `Eta_component` surface. This is the highest seam and carries
   almost every law: declaration errors, admission errors, fences, reports,
   snapshots, change waits, and coeffect-observable component behavior.
   Component behavior under test is expressed through purpose-built test
   coeffects whose values record their own operations.
2. One private trusted semantic driver used only by the conformance and law
   suites. It accepts semantic commands, returns trusted atomic observations,
   and exposes exact causes that production diagnostics keep opaque. The pure
   reference model and this driver share only command and observation types and
   keep separate state representations. This is the one new seam; it stays
   private to the package and adds no public API.
3. The existing `Eta_test.Run` seam for deterministic schedules, ordered
   observations, and the fiber census.
4. The existing `eta_eio` runtime seam for adversarial cancellation and
   cleanup races.
5. Compile-failure fixtures beside the existing `test/type_errors` fixtures,
   for wrong key, configuration, metadata, provision, and release types, and
   for OxCaml mode crossing.
6. Package benchmark rows under `bench/` for the allocation and cost gates.

**Verification layers.** Pure QCheck laws over the deterministic model and
algebraic oracles; `Eta_test` prefix comparison of controlled runtime traces
against every model prefix with a growing identity bijection; `Eta_eio`
adversarial races; compiler and process suites for static rejection.

## Out of Scope

- `eta_component_loader` and `eta_component_loader_native`. They have their own
  specs in this directory.
- An environment parameter on `Effect.t`, Eta layers, and dynamic effect
  provisioning.
- Automatic or callback-based migration of component-local state.
- Source compatibility with the TypeScript Cordis interface, and its mutable
  `Fiber` handles, synchronous internal event channels, random identifiers,

- Distributed brokers, RPC transparency, and cross-process components.
- Compensation for irreversible emissions outside the component context, and
  any recovery claim over external emission history.
- Multiplexing several implementations behind one discoverable coeffect slot.
  That needs an explicit broker component written by the application.
- Zero-gap provider replacement. The global slot can be empty between old

- A default cleanup timeout, a default diagnostic timeout, and any automatic

- A public lifecycle journal or event history, an aggregate availability

- Public capsules, public `unique` or `once` modes, public local modes, public

- Serialization formats, module resolution, interpolation, file watching, and

- An `eta_component_test` package. The reference model, properties, and

- Mechanized proofs of the complete Cordis metatheory, provider package

## Further Notes

Provenance: every decision traces to the
[Eta component runtime map](../../wayfinder/eta-component-runtime/map.md) and
its 23 resolved tickets, with the
[integrated handoff](../../wayfinder/eta-component-runtime/assets/integrated-handoff.md)
as the reconciled contract. The domain terms used here — component, component
instance, component context, coeffect, requirement, provision, consumer,
provider, provider episode, committed provider view, realm, interception
metadata, quarantined component instance, degraded component context — are
already recorded in `CONTEXT.md`.

Validity envelope: the recovery, progress, and confluence claims hold under a
finite acyclic committed graph, paused orchestration input, terminating
activation and cleanup work, successful cleanup, key-defined observational
equivalence, and mediated state. When an assumption fails, the runtime still
preserves lifecycle ownership, admission fences, settlement, and complete
causes, and makes no recovery, progress, or confluence claim. Requirement
`ecrec-fgwo` states the order-independence obligation under exactly those
conditions.

Open matters for implementation time:

- The exact benchmark limits for tracked-ownership registration, one-waiter
  notification, and wall time. Requirement `ecox-wmsl` requires
  recorded baselines first, and only the three zero-allocation rows are fixed
  now.
- Whether the private trusted semantic driver lives in the package as a
  private test-only module or in the test tree. The seam contract is fixed
  either way: semantic commands in, trusted atomic observations out, exact
  causes only for tests.
- The active toolchain cannot build the js_of_ocaml packages, so no JavaScript
  gate covers this package.
